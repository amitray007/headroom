# Decision register

This register distinguishes user requirements from implementation proposals. Date: 2026-10-01.

| ID | Decision | Status | Reason / consequence |
| --- | --- | --- | --- |
| D01 | Open-source, self-hosted web dashboard | User requirement | The user controls the deployment and account data |
| D02 | Browser Connect; no mandatory laptop helper | User requirement | Put integration setup on the host and keep provider approval in the browser |
| D03 | Exclude Zed | User requirement | Avoid research and implementation outside the requested scope |
| D04 | Separate provider dossiers and shared architecture | Implemented in repository | Provider facts change independently |
| D05 | Use Headroom as the project name | User approved | Selected on 2026-10-01; no brand/domain clearance |
| D06 | Prefer official account protocols; ACP optional | Proposed | ACP does not expose all requested account metrics |
| D07 | Persist snapshots; keep credential ownership explicit | Proposed | History and reconnect must survive process exit |
| D08 | Start with a Codex connection proof through the official app-server | Superseded by [ADR 0001](0001-direct-provider-clients.md) | The app-server worker design is replaced by a direct device-code client; Codex stays first |
| D09 | TypeScript and single-host Linux deployment | Confirmed in revised [ADR 0001](0001-direct-provider-clients.md) | TypeScript on Bun; a Go variant was considered on 2026-10-01 and rejected because the reusable packages are TypeScript |
| D10 | SQLite for the first single-host instance | Proposed | Embedded, no cgo, WAL mode; revisit only if a second host appears |
| D11 | MIT for original project material | Applied | Community dependencies and vendor binaries keep their own terms |
| D12 | Reset actions follow read-only monitoring | Proposed | A mutation has different permissions and retry semantics |
| D13 | Official CLI for sign-in only, direct HTTP for refresh and collection | Proposed; see [ADR 0001](0001-direct-provider-clients.md) | CLIs never run on the refresh path; Antigravity uses a direct client; private endpoints labelled and flag-gated |
| D14 | Single dashboard owner in the first release | Proposed | Removes worker tenancy; per-connection isolation remains mandatory |
| D15 | Credentials encrypted at rest in SQLite with an external key file | Proposed | One credential writer per connection; CLIProxyAPI's plaintext files are an optional import, not the store |
| D16 | Private-interface connectors ship behind per-provider enable flags; Claude off by default | Proposed | Policy posture in ADR 0001; the owner opts in per provider |
| D17 | Drop Fireworks | User decision 2026-10-01 | Prepaid balance has no documented route; the private gRPC path is not worth validating for one provider |
| D18 | Credential import of existing CLI or CLIProxyAPI auth files | Proposed | Replaces any laptop-side collector; re-encrypted on paste |
| D19 | Usage endpoints and headers taken from OpenUsage source | Proposed | Most precise current reference; Grok and Copilot routes revised from it |
| D20 | No virtual shell as the CLI runner | Decided 2026-10-01 | just-bash cannot execute native binaries; use `Bun.spawn` or a pseudo-terminal |
| D21 | Stack and tooling baseline: Bun, Hono, Zod, Drizzle on SQLite, Oxlint type-aware, Oxfmt, Knip, TypeScript 7, mise, GitHub Actions | Applied; see [ADR 0002](0002-stack-and-tooling.md) | `mise run check` is the single gate |
| D22 | Better Auth with username, password and passkeys for the single owner; trusted origins from env | User decision 2026-10-01; applied | Replaces the hand-written owner store; see ADR 0002 |
| D23 | Account mutations ship behind the "Allow Account Actions" setting (default off) plus a per-action confirmation; originally also an env flag, removed 2026-10-02 so the setting is the only gate; agents never execute one against a live account, the owner triggers the first run from the dashboard | User decision 2026-10-02; applied for Codex reset consume | A consume spends real inventory; validation of the route is the owner's call |
| D24 | Owner-defined order for providers and accounts, set by dragging in the Connect page's accounts table: providers move freely, accounts only within their provider; stored in `connections.position` and a `display_order` row; drag built natively with pointer events and spring transforms, no drag-and-drop dependency | User decision 2026-10-03; applied | Table rows and grouped constraints fit a small native implementation better than a sortable library; keyboard reordering and live announcements included |
| D25 | Server-side notification delivery to Telegram and webhooks after each scheduler pass; webhooks signed as Standard Webhooks (`webhook-id`, `webhook-timestamp`, `webhook-signature`, HMAC-SHA256, per-channel `whsec_` secret shown once); account email or login added to events only for channels with the identity option on (off by default); `http:` URLs allowed for LAN receivers, credentials in the URL refused; a new channel receives the notices active at its next pass, deduped by event id; retries 1, 5, 15, 60 minutes then stop | User decision 2026-10-03; applied | The owner wants alerts with no browser open. Channel configs are sealed like provider credentials; delivery records hold no secret or response body; see [notifications](../architecture/notifications.md#delivery) |
| D26 | Privacy Mode and Demo Mode are device-local switches in the browser. Privacy Mode (formerly Hide Details, on by default) blurs emails and usernames. Demo Mode (off by default) swaps the overview for a seeded, synthetic one from `@headroom/view-model/demo`: every provider, believable names on reserved example domains (RFC 2606), bounded figures and derived notifications, with a new seed on each page load and each time it turns on. The real overview keeps polling underneath; the web client refuses account mutations while Demo Mode is on; server-side delivery never sees demo data. Privacy Mode blurs demo identities too, so a demo looks like the real app | User decision 2026-10-03, amended 2026-10-07; applied | The owner can show the UI without showing account data. The swap happens in the browser only, so real values still reach the page; Demo Mode suits screen sharing and screenshots, not a public demo instance |
| D27 | Exchange rates come from the European Central Bank's daily reference rates through Frankfurter (`api.frankfurter.dev/v1/latest`, base USD, the supported currencies only). The server fetches them every 24 hours, and on first read when none are cached or they are older than 24 hours; the browser never calls the outside service. They are read-only for the owner: no rate is typed in. The last good rates stay in memory; a failed fetch keeps them, records the error and shows it, and an amount whose currency has no rate stays out of totals instead of being guessed | User decision 2026-10-04; applied | Rates the owner had to keep current went stale and invited mistakes. The ECB publishes one reference rate per day with no key, which suits a monthly subscription total. The rates are not per-transaction exchange rates, so converted totals are approximate. Demo Mode allows the fetch: it reads no account. Since 2026-10-04 the rates are internal to the Wallet, which shows no rates panel. Settings shows the rates and a Refresh button; a refresh fetches at once unless one ran in the last 60 seconds |
| D28 | The Wallet keeps owner-entered money on the server: one cost per connection (`paid`, `free`, `included`, or no row for Not set) in `wallet_costs`, top-ups in `wallet_top_ups`, and the display currency in settings. Amounts are integer minor units with their own currency. Top-ups keep no foreign key, so their record outlives a removed account. The exploration build's browser-only Wallet ran on a local preview only, so no import from it ships. Demo Mode keeps its own Wallet in memory and never writes these tables | User decision 2026-10-04; applied | The Wallet tracks spending so the owner does not have to remember it; entries kept in one browser did not reach the phone or another browser and were lost with site data. See [the data model](../architecture/data-model.md#wallet) and [the API](../architecture/api.md#wallet) |
| D29 | History retention: snapshots and sync runs older than the owner's `historyRetentionDays` setting are deleted, 90 days by default, with 30, 90, 180 and 365 selectable in Settings. Each connection's newest snapshot and newest sync run are always kept. The scheduler prunes on its first tick after startup and then at most every six hours, reading the setting each time | User decision 2026-10-04; applied | Unbounded history grows with every refresh while the dashboard reads only the latest reading. Metrics and reset credits follow their snapshot through the cascade; an action row that referenced a pruned snapshot loses only that link. See [the data model](../architecture/data-model.md#retention) |
| D30 | Every connector request goes through `timeoutFetch` in `packages/core/src/http.ts`: a 20-second timeout that classifies as transient `provider_unavailable`, and redirects followed by Headroom, at most five hops. A cross-origin hop drops every credential-bearing header (authorization, cookies, tokens, keys, account ids); an https-to-http hop is refused. Status codes map through one shared ladder with one `Retry-After` reader clamped to one minute..one hour. Shared CLI sign-in polling lives in `packages/core/src/cli-login.ts` | Code review 2026-10-04; applied | A hung request stalled the serial scheduler and could outlive the two-minute collection lease, letting a second holder rotate the same refresh token. Following redirects in the runtime would forward an Authorization header to whatever host a redirect names. Seven copies of the status ladder had already diverged |
| D31 | Owner automations: account events detected between readings (new banked reset, early reset, top-up), detected top-ups recorded in the Wallet with `source: "detected"`, a per-account Codex auto-reset rule that runs through the action service with `origin: "automation"`, owner spend budgets, and Wallet credit expiry notices. Headroom never buys credits | User decision 2026-10-04; see [ADR 0003](0003-owner-automations.md) | Amends the monitoring rule in AGENTS.md and D23: an owner-configured rule counts as an explicit owner action |
| D32 | Per-provider display choices live in server settings under `providers`, edited in a Settings tab of the same name that lists only connected providers with a choice. The first is `hideZeroBalance`, one rule for every balance figure of the provider (for Claude today, Usage Credits and Cloud Credits): balances show $0.00 by default and the owner can hide any balance while it is exactly 0. Spend figures never hide, and an unread balance still shows as unknown. Cloud Credits (`iguana_necktie`) join the same `credits_expiring` and `balance_low` notices. Claude usage-credit notices reuse `balance_low` (ran out while extra usage is on), `credits_expiring` (on `resetLeadDays`) and `top_up_detected` (USD, no Wallet row) | User decision 2026-10-08; applied | A zero balance is a real figure, so it shows unless the owner says otherwise. A per-provider object leaves room for later display choices without one top-level key each. The Wallet counts credits, so a money rise stays an event only |
| D33 | Releases follow Semantic Versioning, chosen by release-please from Conventional Commit subjects on `main`. The first release is `0.1.0`. Before `1.0.0` a feature bumps the patch and a breaking change the minor; the owner raises the minor or major on purpose with the `Release As` workflow, which commits a `Release-As` footer (owner decision 2026-10-09). Merging the release pull request tags `vX.Y.Z` and publishes a multi-arch image to GHCR: `X.Y.Z`, `X.Y`, `X` from 1.0, and `latest` per release, `edge` per push to `main`, each only after a smoke test of the pushed image. The binary is cross-compiled on the build platform, so only the runtime stage is emulated | User decision 2026-10-09; applied | Fix or feature is recorded once, in the commit, and the version, changelog and image tags follow from it. A tested-then-tagged image never leaves `latest` on a broken build. See [Releases](../operations/releases.md) |
| D34 | The public demo is a static build of the web app, `mise run demo:build` (`vite build --mode demo`, output `apps/web/dist-demo`, relative base for a sub-path). It runs the real app on Demo Mode's synthetic data with no server: `apps/web/src/demo-site/` answers every `/api/` request in the page, signs in a synthetic owner, keeps Demo Mode on, starts with Privacy Mode off, and refuses every change with "This is a demo. Deploy your own Headroom to use this." ("...to connect accounts." on Connect), and hides passkeys, password and sign-out. With `?embed=1` it drops its banner and talks to a same-origin parent page by `postMessage` (`navigate`, `scheme` in; `ready`, `route` out). A normal build contains none of this code; only a late-bound `fetch` in the Better Auth client is shared | User decision 2026-10-09; applied | Visitors use the real app without an account, and no one runs a server holding demo data. D26 still holds for a deployed instance: Demo Mode there is for screen sharing, not a public demo |
| D35 | The public site is `site/index.html`, a single static page with no framework, built by `mise run site:build` into `dist-site/` with the demo (D34) at `demo/`, and deployed to GitHub Pages by `pages.yml` after each release. It embeds the demo in an iframe at a fixed logical size (1200 x 750, or 390 x 800 on phones), scaled to fit. While the demo loads, the page shows a skeleton that `scripts/site.ts` reads from the fresh demo build in headless Chrome through `playwright-core` (a pinned dev dependency, no browser download): the app's loading top bar plus the demo's first screen with every value turned into a placeholder, in both colour schemes | User decision 2026-10-09; applied | The visitor uses the real app, and the swap from skeleton to app changes only the placeholders. Reading the skeleton from the build keeps it true to the dashboard; the `site` job in CI fails when a dashboard change breaks it |
